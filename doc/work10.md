# work10 - 内部刷新接口与全局拦截增强技术实现报告

## 1. 目标与范围

本报告本次完成的核心工作，详细介绍以下功能的实现逻辑、设计思想与配套代码工作：

- `/innerApi/refresSysSetting` 内部接口开发
- 全局拦截器中的操作频率校验能力
- 开发模式下“无需登录”的联调支持能力
- 论坛 Web 端阶段性收尾与后续优化方向

报告风格延续 work09，重点聚焦控制层、切面层、服务层与配置层的协同设计。

## 2. 总体设计思路

### 2.1 设计目标

本次改造围绕“可运维、可控流、可联调”三个目标展开：

- 可运维：管理端修改系统设置后，Web 端可立即刷新内存配置，避免重启。
- 可控流：对发帖、评论、点赞、图片上传等高频操作做统一频率限制。
- 可联调：在开发环境下自动注入测试登录态，降低接口联调门槛。

### 2.2 分层职责

- 控制层
  - 承接内部刷新请求，完成签名校验与响应包装。
- AOP 切面层
  - 统一处理登录校验、参数校验、频率校验、成功后计数。
- 服务层
  - 提供系统设置加载与缓存写入能力。
- 配置层
  - 通过 `application.yml` 与 `WebConfig/AppConfig` 管理安全密钥和环境开关。

## 3. `/innerApi/refresSysSetting` 接口实现

### 3.1 功能定位

该接口用于“管理端修改系统配置后，通知论坛 Web 端刷新内存中的系统设置”，本质是一次受保护的内部控制指令。

### 3.2 接口定义与输入

接口位于 `InnerApiController`，路由前缀 `/innerApi`，方法映射 `/refresSysSetting`。

输入参数：

- `appKey`：应用标识（必填）
- `timestamp`：时间戳（必填）
- `sign`：签名串（必填）

并通过 `@GlobalInterceptor(checkParams = true)` 启用参数存在性校验。

### 3.3 核心校验逻辑

控制器内依次执行以下安全校验：

1. `appKey` 一致性校验
   - 与配置中的 `inner.api.appKey` 比对，不一致直接拒绝。
2. 时间窗校验
   - 校验 `System.currentTimeMillis() - timestamp <= 10s`，防止重放请求。
3. 签名校验
   - 使用 `md5(appKey + timestamp + innerApiAppSecret)` 生成本地签名，与传入 `sign` 比对。

校验全部通过后，调用 `sysSettingService.initSysSettingToCache()` 完成刷新，并返回最新 `SysSettingDto`。

### 3.4 缓存刷新链路

`initSysSettingToCache()` 的实现过程：

1. 查询数据库全部系统配置项。
2. 按 `code` 匹配 `SysSettingCodeEnum`，确定目标 DTO 字段及反序列化类型。
3. 将每条 JSON 配置内容反序列化并写入 `SysSettingDto`。
4. 通过 `SysCacheUtils.setSysSettingMap(sysSettingDto)` 原子替换内存缓存。
5. 返回最新缓存对象给调用方。

### 3.5 设计要点

- 使用“内部接口 + appKey/appSecret + 时间窗签名”组合，满足轻量级安全要求。
- 刷新逻辑与业务请求解耦，避免普通请求中夹杂配置重载。
- 缓存采用 `ConcurrentHashMap`，在多线程读写场景下具备并发安全基础。

## 4. 全局频率校验实现

### 4.1 架构入口

频率校验集成于 `OperationAspect` 的环绕通知流程中：

1. 若注解要求，先做登录校验。
2. 若注解要求，做参数校验。
3. 执行 `checkFrequency(frequencyType)` 进行频率限制。
4. 执行业务方法。
5. 若响应成功，执行 `addOpCount(frequencyType)` 计数累加。

该流程将“限流规则”从业务控制器中抽离，实现统一治理。

### 4.2 注解驱动能力

`GlobalInterceptor` 新增/使用 `frequencyType` 枚举参数，默认 `NO_CHECK`。

已接入典型场景：

- 发帖：`POST_ARTICLE`
- 发评论：`POST_COMMENT`
- 点赞：`DO_LIKE`（文章与评论）
- 上传图片：`IMAGE_UPLOAD`

### 4.3 频率判定策略

`checkFrequency` 以“用户 + 日期 + 操作类型”为维度统计：

- session key：`SESSION_KEY_FREQUENCY + yyyy-MM-dd + typeEnum`
- 若 session 中无计数：
  - 发帖/评论/点赞从数据库回查当天历史计数
  - 图片上传从 0 开始（当前版本）
- 与系统配置阈值比对：
  - 发帖阈值：`postDayCountThreshold`
  - 评论阈值：`commentDayCountThreshold`
  - 点赞阈值：`likeDayCountThreshold`
  - 图片阈值：`dayImageUploadCount`
- 超限抛出业务异常，阻断业务执行。

业务方法成功返回后，`addOpCount` 将 session 计数加 1，形成“校验前读、成功后写”的闭环。

### 4.4 设计要点

- 统一限流入口，避免各控制器重复造轮子。
- 首次从数据库回查可兼容“服务重启后 session 无计数”的场景。
- 仅在成功响应后累加计数，避免失败请求误伤配额。
- 已在代码中注明后续方向：频率能力迁移到 Redis 以支持分布式与跨会话一致性。

## 5. 开发态免登录能力实现

### 5.1 触发条件

在 `checkLogin()` 中，当以下条件同时满足时触发开发态自动登录：

- 当前 session 无登录用户
- `isDev.open = true`

### 5.2 处理逻辑

1. 使用 `isDev.testUserEmail` 查询测试账号。
2. 若不存在则自动创建测试用户（含基础积分、昵称、状态）。
3. 组装 `SessionWebUserDto`（默认管理员权限）写入 session。
4. 后续请求可按“已登录态”继续执行。

### 5.3 设计价值

- 降低本地调试与前后端联调成本，无需重复执行登录流程。
- 使依赖登录态的接口在开发环境可快速验证业务逻辑。
- 通过环境开关隔离开发与生产行为，避免生产越权风险。
