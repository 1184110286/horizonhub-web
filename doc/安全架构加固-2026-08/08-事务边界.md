# 08 补齐事务边界

> 涉及提交：

> - `8618a17` fix: 评论批量删除/审核补外层事务

## 原来的实现

### updateArticle：多表写但无事务

`ForumArticleServiceImpl.updateArticle` 在一个方法内跨 `forum_article` 与 `forum_article_attachment` 多表写：

```java
@Override
public void updateArticle(...) throws BusinessException {
    // 判断文章所属权
    ForumArticle dbInfo = forumArticleMapper.selectByArticleId(...);
    ...
    // 可能 insert/update 附件（uploadAttachment 内部）
    if (attachment != null) { uploadAttachment(article, ..., true); }
    // 可能 deleteByFileId / updateByFileId 附件
    ...
    forumArticleMapper.updateByArticleId(article, article.getArticleId());   // 更新文章
}
```

但这个方法**没有 `@Transactional`**（对比同文件 `postArticle` 有 `@Transactional`，明显是遗漏）。

### 批量删除 / 审核：循环内各自有事务，外层无整体事务

```java
@Override
public void delArticle(String articleIds) {
    String[] articleIdArray = articleIds.split(",");
    for (String articleId : articleIdArray) {
        forumArticleService.delArticleSingle(articleId);   // 每个 *Single 有 @Transactional
    }
}
```

`auditArticle` / 评论的 `delComment` / `auditComment` 同样模式。

## 存在的问题

- **updateArticle 数据不一致**：跨多表写无事务，若中途异常（附件已删 / 已改、文章未更新），数据库留下不一致状态。
- **批量操作部分成功**：管理员「批量删除 10 篇」时，若第 5 篇抛异常，前 4 篇已删、后 6 篇未删。结果既不原子，也无法给前端明确反馈。
  - 注意：单个 `*Single` 方法的事务**是生效的**——因为循环里通过注入自身代理 `forumArticleService.delArticleSingle(...)` 调用，规避了 self-invocation。这点原本就做对了；缺的只是「外层批量」的原子性。
- AI 代理代用户发帖 / 改帖走的就是 `postArticle` / `updateArticle` 路径，必须保证数据一致性。

## 改进后的实现

为缺事务的方法补上 `@Transactional(rollbackFor = Exception.class)`：

```java
// updateArticle（修复多表写缺事务）
@Override
@Transactional(rollbackFor = Exception.class)
public void updateArticle(...) throws BusinessException { ... }

// 批量删除文章（整体原子）
@Override
@Transactional(rollbackFor = Exception.class)
public void delArticle(String articleIds) { ... }

// 批量审核文章
@Override
@Transactional(rollbackFor = Exception.class)
public void auditArticle(String articleIds) { ... }

// 评论同理（ForumCommentServiceImpl）
@Override
@Transactional(rollbackFor = Exception.class)
public void delComment(String commentIds) { ... }

@Override
@Transactional(rollbackFor = Exception.class)
public void auditComment(String commentIds) { ... }
```

## 如何工作（改造后）

- **updateArticle**：现在整个方法在一个事务内，任何子步骤异常都会回滚，文章与附件保持一致。
- **批量删除 / 审核**：外层方法整体事务，任一篇 / 一条异常则全部回滚，要么全成功要么全不动（原子）。`rollbackFor = Exception.class` 确保非 RuntimeException（如 IOException）也回滚。
- 外层 `@Transactional` 与内层 `*Single` 的 `@Transactional` 默认传播级别都是 `REQUIRED`：内层加入外层事务，不会各开各的，因此「外层包内层」是一个完整事务。

## 刻意延后（非遗漏）

**`postArticle` 的文件 IO 移出事务**未做：

- 该方法**本身有** `@Transactional`（事务边界存在），但封面 / 附件的**文件上传发生在事务方法体内**。磁盘 / 网络上传是慢 IO，持有 DB 事务不释放会导致长事务、占用连接池。
- 原计划改为「先在事务外完成文件上传拿到 path，再开启短事务做 DB 写入」，但因该法逻辑复杂（封面 / 附件 / 正文图片路径重写 / 积分发放交织）且当时无法可靠编译验证，判定为高风险重构而暂缓。
- `updateArticle` 的文件 IO 同样仍在事务内（但其缺事务的 bug 已修复）。

## 验证 / 注意事项

- 事务生效依赖 Spring 代理：批量方法必须通过 Bean 调用（Controller 调 Service）才生效——现有调用链均满足。
- self-invocation 陷阱：`delArticle` 内部调 `forumArticleService.delArticleSingle(...)`（注入的是代理对象）而非 `this.delArticleSingle(...)`，所以内层 `@Transactional` 生效；改造时保持了这一写法，勿改成 `this.`。
- 若希望批量「部分成功并收集失败项返回前端」（而非全成功全不动），需要另一套设计（去掉外层事务 + 收集异常），当前选择了更安全的「原子」策略。
