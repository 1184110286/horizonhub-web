# 01 公共模块抽取（horizonhub-common）

> 涉及提交：`b7b999c` refactor: 抽取公共参数校验切面与文件访问基类到 common 模块

## 原来的实现

改造前，`horizonhub-web` 与 `horizonhub-admin` 两个模块各自维护一份几乎相同的切面与文件控制器，存在**逐字符重复**。

### 1. 两套 OperationAspect（参数校验逻辑 100% 重复）

- `horizonhub-web/.../aspect/OperationAspect.java`
- `horizonhub-admin/.../aspect/OperationAspect.java`

两者都通过 `@Around("@annotation(GlobalInterceptor)")` 拦截，并各自实现了完全一致的参数校验三件套：

```java
private static final String[] TYPE_BASE = {
        "java.lang.String", "java.lang.Integer", "java.lang.Long"
};

private void validateParams(Method m, Object[] arguments) { ... }
private void checkObjValue(Parameter parameter, Object value) {
    // 每次请求现场 Class.forName + getDeclaredFields + setAccessible + field.get
    ...
}
private void checkBasicTypeValue(Object value, VerifyParam verifyParam) { ... }
```

区别仅在于：**web 版额外承担了操作频率限制**（Redis Lua 原子计数、回滚、DB 回源），admin 版是子集、没有限流。

### 2. 两套 FileController（约 100 行重复）

- `horizonhub-web/.../controller/FileController.java`
- `horizonhub-admin/.../controller/FileController.java`

`getAvatar` / `getImage` / `readImage` / `printNoDefaultImage` 完全相同，唯一的差异是项目根目录的来源——web 取自 `WebConfig`，admin 取自 `AdminConfig`（二者都继承自 `AppConfig.getProjectFolder()`）。

## 存在的问题

- **重复代码**：两套实现，一旦演进必然分叉，维护成本翻倍。
- **引入 AI 模块会放大问题**：计划新增的 `horizonhub-ai` 入口模块若复用同样的切面 / 文件访问逻辑，重复会从 2 份变成 3 份。这是「接 AI 前最关键的架构动作」——必须先把公共能力下沉。
- 频率限流逻辑（web 独有）和参数校验逻辑（两者共有）耦合在同一个切面里，职责混杂。

## 改进后的实现

将公共部分下沉到 `horizonhub-common`，web 端独有部分保留在 web。

### 1. common 新增 `ParamValidateAspect`（参数校验切面）

`horizonhub-common/.../aspect/ParamValidateAspect.java`，承载原来两者共有的参数校验逻辑，用 `@Order(10)` 声明为「外层」：

```java
@Component
@Aspect
@Order(10)
public class ParamValidateAspect {
    @Around("@annotation(com.nlizzard.horizonhub.annotation.GlobalInterceptor)")
    public Object around(ProceedingJoinPoint point) throws Throwable {
        ...
        if (interceptor.checkParams()) {
            validateParams(method, arguments);
        }
        return point.proceed();
    }
}
```

### 2. web 新增 `FrequencyLimitAspect`（频率限流切面）

`horizonhub-web/.../aspect/FrequencyLimitAspect.java`，只保留频率控制（Redis Lua 脚本、预占 / 回滚 / 回源），用 `@Order(20)` 声明为「内层」。**参数校验职责已上提到 common，本切面不再重复校验。**

### 3. common 新增 `BaseFileController`（文件访问基类）

`horizonhub-common/.../basecontroller/BaseFileController.java`（继承 `BaseController`），承载 `getAvatar` / `getImage` / `readImage` / `printNoDefaultImage`，并定义抽象方法让子类提供根目录：

```java
public abstract class BaseFileController extends BaseController {
    /** 子类提供项目根目录（web 取自 WebConfig，admin 取自 AdminConfig）。 */
    protected abstract String getProjectFolder();
    ...
}
```

两个 `FileController` 改为继承它：admin 版只剩一个 `getProjectFolder()` 实现；web 版额外保留图片上传 `uploadImage`。

### 4. 旧的 OperationAspect 降级为空壳

`OperationAspect.java`（web / admin）因提交期间无法物理删除文件，被降级为空 `@Deprecated` 桩类（不挂切面、不参与拦截），待后续物理删除。

## 如何工作（改造后）

- **两个应用都扫描 `com.nlizzard.horizonhub` 根包**，因此 common 里的 `ParamValidateAspect` 会自动被两个模块的组件扫描拾取，无需额外配置。
- **同一注解、两个切面、靠 `@Order` 串起来**：web 端一个标注了 `@GlobalInterceptor` 的方法，请求进入时先由外层 `ParamValidateAspect`（@Order 10）做参数校验，校验通过后再进入内层 `FrequencyLimitAspect`（@Order 20）做频率预占。这样保证「参数不合法时不会白白消耗频率配额」。
- admin 端没有频率限流需求，只有 common 的 `ParamValidateAspect` 生效。
- `BaseFileController` 通过模板方法让两个子类复用全部文件访问能力，仅注入各自的配置来源。

## 验证 / 注意事项

- 切面顺序依赖 `@Order`：若未来新增切面，注意它与 10 / 20 的相对顺序。
- 空壳 `OperationAspect` 待删除：在 IDE 里会显示无引用，可安全物理删除。
