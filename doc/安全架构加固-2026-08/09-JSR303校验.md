# 09 引入 JSR-303 校验基础设施与全局异常增强

> 涉及提交：`fa888fb` feat: 引入 JSR-303 校验基础设施与全局异常增强
> 依赖引入：`5c9f0d7` chore: 引入密码加密、富文本净化、参数校验依赖

## 原来的实现

### 自研参数校验（`@VerifyParam` + 反射切面）

项目用自定义注解 `@VerifyParam`（`required/min/max/regex`）配合切面反射校验：

- 仅支持 **String / Integer / Long** 三种基础类型（`TYPE_BASE`）。
- 对象类型靠反射 `getDeclaredFields()` **单层扫描**，**不支持嵌套对象、集合元素校验、自定义 Validator、分组校验**。
- 每次请求现场 `Class.forName` + `getDeclaredFields` + `setAccessible` + `field.get`，无缓存。
- 错误消息硬编码（「缺少必填字段」「参数长度必须在 x-y 之间」），无法定位具体字段。

### 全局异常处理覆盖不全

`GlobalExceptionHandlerController` 只处理了 5 类异常：

```java
if (e instanceof NoHandlerFoundException) { ... }
else if (e instanceof BusinessException biz) { ... }
else if (e instanceof BindException) { ... }       // 参数类型错误
else if (e instanceof DuplicateKeyException) { ... }
else { /* 500 兜底 */ }
```

未覆盖：上传超限、参数类型不匹配、JSON body 损坏、缺必填参数、不支持的 HTTP 方法等。

## 存在的问题

- **自研校验是 AI 功能的硬瓶颈**：AI 对话返回的会是**复杂嵌套 DTO**（如「发帖」参数含 article + attachment + cover）。`@VerifyParam` 既不支持嵌套也不支持集合元素校验，无法承载 AI 场景。
- **异常被吞成 500**：本项目大量文件上传，超限（`MaxUploadSizeExceededException`）会被兜底成「服务器返回错误」，用户无法理解；`Integer` 传成字符串等也类似。
- 自研反射校验性能与可维护性差。

## 改进后的实现

### 1. 引入 spring-boot-starter-validation（在 `5c9f0d7`）

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-validation</artifactId>
</dependency>
```

提供 `jakarta.validation` 约束注解（`@NotBlank` / `@Size` / `@Email` / `@Pattern` / `@Valid` 等）。

### 2. 增强全局异常处理

`GlobalExceptionHandlerController` 新增针对 JSR-303 与常见 Spring MVC 异常的细粒度处理：

```java
@ExceptionHandler(MethodArgumentNotValidException.class)       // @RequestBody + @Valid 失败
ResponseVO<Void> handleArgNotValid(MethodArgumentNotValidException e) { ... }   // 返回具体字段消息

@ExceptionHandler(ConstraintViolationException.class)          // @RequestParam/@PathVariable 约束失败
ResponseVO<Void> handleConstraintViolation(ConstraintViolationException e) { ... }

@ExceptionHandler(MaxUploadSizeExceededException.class)        // 上传超限 → 明确提示
ResponseVO<Void> handleUploadSize(...) { ... }

@ExceptionHandler(MethodArgumentTypeMismatchException.class)   // Integer 传成字符串
@ExceptionHandler(MissingServletRequestParameterException.class)  // 缺必填参数
@ExceptionHandler(HttpMessageNotReadableException.class)       // JSON body 损坏
@ExceptionHandler(HttpRequestMethodNotSupportedException.class)  // GET 打 POST 接口（配合 05）
...
@ExceptionHandler(Exception.class)                             // 原有兜底逻辑保留
```

每个细粒度处理都映射到 `CODE_600` + 可读消息，而非 500。

### 3. 与现有 `@VerifyParam` 并存

**不破坏现有接口**：现有的 `@VerifyParam` + `ParamValidateAspect`（见 [01-公共模块抽取.md](01-公共模块抽取.md)）继续工作；JSR-303 只是作为「新增能力」就位。

## 如何工作（改造后）

- **现有接口**：仍走 `@GlobalInterceptor(checkParams=true)` → `ParamValidateAspect` 的 `@VerifyParam` 反射校验，行为不变。
- **新增 / AI 场景接口**：可在 DTO 字段加 `@NotBlank/@Size/@Email/@Pattern`，Controller 形参加 `@Valid`；校验失败时 Spring 抛 `MethodArgumentNotValidException`，被新增的 handler 捕获，返回带**具体字段错误消息**的 `CODE_600`。
- **统一错误体验**：上传超限、类型不匹配、方法不支持等，都从「500 服务器错误」变成「600 参数错误 + 可读提示」，前端能正确展示。
- 配合 [05-写接口POST.md](05-写接口POST.md)：对 POST 接口发起 GET 会抛 `HttpRequestMethodNotSupportedException`，现在被优雅处理。

## 验证 / 注意事项

- **本轮只落地基础设施**，未把现有接口迁移到 JSR-303（避免大面积回归）。迁移可在逐个接口改造时渐进进行。
- 若要在 `@RequestParam` / `@PathVariable` 上用约束注解，Controller 类需加 `@Validated`（本基础设施已支持，迁移时注意补注解）。
- `@Valid` 校验嵌套对象时，嵌套字段需标注 `@Valid`，否则只校验第一层——AI 场景的嵌套 DTO 要留意。
