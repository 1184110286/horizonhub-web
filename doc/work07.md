# work07 - 文件上传与评论发布模块开发总结（FileUtils / FileController / postComment）

## 一、概述

本次工作主要围绕“**文件上传与访问能力补齐**”以及“**发表评论能力闭环**”两条主线展开，完成了以下 3 块核心内容：

- 通用文件上传工具类：`FileUtils`
- 文件接口开发：`/file/uploadImage`、`/file/getAvatar/{userId}`、`/file/getImage/{imageFolder}/{imageName}`
- 评论发布接口开发：`/comment/postComment`

这几部分能力不是孤立完成的，而是共同构成了一条完整链路：

- 前端可以先上传图片，拿到访问路径；
- 服务端可以根据业务类型把图片落到不同目录；
- 评论发布时既支持纯文本评论，也支持带图片评论；
- 文件接口负责将头像、临时图片、正式图片稳定输出给前端页面使用。

如果从系统职责上看，本次工作的分层比较清晰：

- `Controller` 层负责接口入口、参数校验、登录校验与基础兜底；
- `Service` 层负责评论发布的核心业务规则；
- `FileUtils` 负责统一的本地文件上传策略；
- `Constants`、`FileUploadTypeEnum`、`SysCacheUtils` 等通用组件负责目录常量、上传类型约束与系统开关配置。

文档会重点介绍本次实现的设计思路、关键实现细节和业务联动逻辑，而不是只停留在“接口已经写完”的层面。

## 二、通用文件上传能力：`FileUtils`

### 1. 工具类作用

`FileUtils` 的定位不是某一个接口的附属工具，而是整个项目中统一的文件上传入口。它的核心目标有 3 个：

- **统一校验规则**：不同业务类型的文件后缀校验逻辑集中处理；
- **统一目录策略**：图片、附件、头像按照固定目录规范保存；
- **统一返回结构**：上传后返回本地相对路径和原始文件名，方便业务层继续使用。

对应实现位置：

- `horizonhub-common/src/main/java/com/nlizzard/horizonhub/utils/FileUtils.java`

### 2. 入参与返回值设计

`uploadFile2Local` 方法的入参包括：

- `MultipartFile file`：上传的文件对象
- `FileUploadTypeEnum uploadTypeEnum`：上传类型枚举
- `String folder`：业务目录名或头像场景下的用户标识

返回值为 `FileUploadDto`，包含两个字段：

- `localPath`：文件在项目文件目录下的相对路径
- `originalFilename`：上传时的原始文件名

这种设计比直接返回一个字符串更稳妥，原因在于后续不同业务往往既需要访问路径，也需要展示原始文件名。例如：

- 评论图片更关注访问路径；
- 附件类文件未来还可能需要展示“原文件名”。

### 3. 通过枚举统一上传类型

为了避免给“文章封面、评论图片、附件、头像”分别写一套独立上传逻辑，本次实现使用了 `FileUploadTypeEnum` 来做统一分流：

- `ARTICLE_COVER`
- `ARTICLE_ATTACHMENT`
- `COMMENT_IMAGE`
- `AVATAR`

枚举中直接绑定允许的后缀集合：

- 图片类使用 `Constants.IMAGE_ALL_SUFFIX`
- 附件类使用 `Constants.ATTACHMENT_ALL_SUFFIX`

这样带来的好处是：

1. 校验规则集中，后续扩展上传类型时改动范围小；
2. Controller 或 Service 层只需要关心“这是什么业务类型”，不需要重复写后缀判断；
3. 不同上传场景可以在一个工具类中共享目录组织、命名规则、异常处理逻辑。

### 4. 文件合法性校验

上传逻辑开始后，先获取原始文件名并提取后缀：

- 通过 `MultipartFile#getOriginalFilename()` 获取原始文件名；
- 通过 `StringTools.getFileSuffix(...)` 提取文件后缀；
- 使用 `ArrayUtils.contains(uploadTypeEnum.getSuffixArray(), fileSuffix)` 做白名单校验。

如果后缀不在当前上传类型允许的范围内，则直接抛出业务异常：

- `throw new BusinessException("文件类型不正确")`

这一步的设计重点是：**上传类型决定文件白名单**。

也就是说，系统并不是简单判断“是不是图片”，而是根据当前业务上下文判断“这个接口此刻允许接收什么类型的文件”。这样比把所有校验散落在各个接口中更容易维护。

### 5. 文件名长度控制与唯一命名策略

本次实现中，对原始文件名做了两层处理。

#### 5.1 过长文件名裁剪

如果原始文件名长度超过 `Constants.LENGTH_200`，则保留文件主名的前 `190` 个字符，再拼回后缀。

这么做的目的主要有两点：

- 防止极长文件名导致磁盘路径过长；
- 保留尽量多的原始信息，避免后续展示时完全失去文件可读性。

#### 5.2 雪花算法生成唯一文件名

真实保存到服务器的文件名并不直接使用原始文件名，而是通过：

- `IdUtil.getSnowflakeNextIdStr()`

生成唯一 ID，再拼接原始后缀。

这种策略解决了两个问题：

- 避免同名文件覆盖；
- 保证高并发上传场景下文件名仍具备全局唯一性。

### 6. 目录组织策略

#### 6.1 普通文件按月份归档

对于文章图片、评论图片、附件等普通上传场景，文件会按月份分目录保存。核心实现逻辑是：

- 使用 `DateUtil.format(new Date(), DateTimePatternEnum.YYYY_MM.getPattern())` 生成如 `2026/03` 这样的月份字符串；
- 最终目录结构为：`projectFolder + /file + 业务目录 + 月份目录`

例如评论图片可能被存储到：

- `/file/images/2026/03/xxx.jpg`

按月份分目录的好处很明显：

- 单个目录下文件数量不会无限膨胀；
- 后续按时间清理、迁移、定位问题更方便；
- 对文章图片、评论图片等高频上传资源更友好。

#### 6.2 头像走特殊目录规则

头像与普通图片不同，本次实现对头像做了特殊处理：

- 不再按月份分目录；
- 直接保存到 `/file/avatar/` 下；
- 文件名固定为 `{userId}.jpg`。

也就是说，头像的 `folder` 参数并不是月份目录，而是当前用户 ID。

这样设计的优点是：

- 用户头像访问路径稳定；
- 更新头像时可以直接覆盖旧头像；
- 头像读取接口无需查数据库即可按用户 ID 直接定位文件。

### 7. 差异化处理：评论图片缩略图与附件处理

统一上传入口并不意味着所有文件都一视同仁，本次实现保留了业务差异化处理。

#### 7.1 评论图片自动生成缩略图

当上传类型为 `COMMENT_IMAGE` 时，上传完成后会额外生成一张缩略图：

- 新文件名在原文件名基础上增加 `_`
- 使用 `ImgUtil.scale(...)` 生成 `200 x 200` 的缩放图
- 空白区域用 `Color.WHITE` 填充

这类处理比较适合评论区展示场景，原因是评论区里的图片通常不需要直接以原图尺寸渲染，缩略图可以降低首屏展示成本，也便于前端在列表场景下统一展示风格。

#### 7.2 附件场景的特殊分支

当上传类型为 `ARTICLE_ATTACHMENT` 时，也进入了额外处理分支。

从当前实现来看，它同样调用了 `ImgUtil.scale(...)`。这说明该分支已经预留了“附件类文件特殊处理”的统一入口，后续如果要针对附件生成封面图、预览图或做进一步处理，可以直接沿着当前结构继续扩展。

### 8. 异常处理思路

整个上传流程对异常做了两层兜底：

- 如果是业务异常，记录日志后继续向上抛出；
- 如果是其他未知异常，统一包装成 `BusinessException("文件上传失败")`

这种处理方式可以保证：

- 合法的业务错误信息不会丢失；
- 底层异常细节不会直接暴露给前端；
- 日志中仍然保留完整栈信息，方便排查问题。

## 三、文件接口开发明细：`FileController`

对应实现位置：

- `horizonhub-web/src/main/java/com/nlizzard/horizonhub/controller/FileController.java`

本次在 `FileController` 中完成了 3 个对外接口，以及配套的文件保存与读取逻辑。整体职责可以概括为：

- 为富文本或页面交互提供图片上传入口；
- 为用户头像提供稳定读取入口；
- 为普通图片、临时图片、头像图片提供统一输出能力。

### 1. `/file/uploadImage` —— 图片上传接口

#### 1.1 接口作用

该接口用于接收前端上传的图片，并返回图片的相对访问路径。

从当前实现来看，它主要服务于“先上传图片，再在页面中引用”的交互场景，例如：

- 富文本编辑器插入图片；
- 页面表单中先上传图片再提交业务数据。

#### 1.2 参数与约束

- 入参：`MultipartFile file`
- 需要登录：`@GlobalInterceptor(checkLogin = true)`

接口中做了两层基础校验：

1. 文件不能为空；
2. 文件后缀必须是图片类型。

如果文件为空，则抛出：

- `请选择要上传的图片`

如果后缀不在 `Constants.IMAGE_ALL_SUFFIX` 中，则抛出：

- `文件格式不支持`

#### 1.3 实现思路

该接口没有直接复用 `FileUtils`，而是走了一个更轻量、更偏页面交互的实现：

- 从原始文件名中提取后缀；
- 使用雪花算法生成新的文件名；
- 将图片先保存到 `/file/temp/` 临时目录；
- 返回 `temp/文件名` 给前端。

这种实现非常适合“正文尚未正式提交，但图片已经先上传”的场景。临时目录的意义在于：

- 文件可以先存在服务器上，避免用户提交大段正文时再次上传图片；
- 页面可以即时预览上传结果；
- 后续如果业务保存成功，再决定是否将这些资源转正、引用或清理。

#### 1.4 返回结果

接口最终返回：

- `ResponseVO<Map<String, String>>`

其中 `fileName` 字段保存的是相对路径，例如：

- `temp/123456789.jpg`

这样前端只要配合图片读取接口，就可以直接完成展示。

### 2. `/file/getAvatar/{userId}` —— 用户头像读取接口

#### 2.1 接口作用

该接口用于根据用户 ID 获取头像图片。

它的设计目标很明确：

- 前端无需关心头像的物理存储路径；
- 如果用户没有上传头像，系统自动回退到默认头像；
- 如果默认头像也不存在，则给出清晰提示。

#### 2.2 参数与约束

- 路径参数：`userId`
- 使用 `@GlobalInterceptor(checkParams = true)` 对参数做基础校验
- `userId` 使用 `@VerifyParam(required = true)` 标记为必填

#### 2.3 关键实现逻辑

当前头像读取逻辑采用的是“**用户头像 -> 默认头像 -> 文本提示**”三级降级策略。

第一步，优先尝试读取：

- `/file/avatar/{userId}.jpg`

如果该文件不存在，则继续尝试读取：

- `/file/avatar/default_avatar.jpg`

如果默认头像也不存在，则调用 `printNoDefaultImage(response)`，直接向响应流输出提示信息：

- `请在头像目录下放置默认头像default_avatar.jpg`

这个设计虽然简单，但很实用，原因在于：

- 即使数据库里没有显式记录头像路径，也能根据用户 ID 直接访问头像；
- 在资源缺失时不会无响应，便于开发或部署阶段快速发现问题；
- 默认头像机制保证页面不会因为个别用户未上传头像而出现空白图。

#### 2.4 当前实现特点

代码中已经明确写了 TODO：

- 当前头像默认按 `.jpg` 读取；
- 后续可以扩展支持 `.png` 等格式；
- 当前 `user_info` 表中没有存储头像路径。

这说明当前方案更偏“约定优于配置”：

- 头像名按用户 ID 固定命名；
- 头像路径通过文件目录规则推导；
- 读取逻辑简单直接，省去了数据库层映射成本。

### 3. `/file/getImage/{imageFolder}/{imageName}` —— 通用图片读取接口

#### 3.1 接口作用

该接口用于统一读取项目中的图片资源，支持以下几类目录：

- 正式图片目录：`images`
- 临时图片目录：`temp`
- 头像目录：`avatar`

它对前端的意义在于：

- 前端只需要传目录名和文件名；
- 不需要知道项目在服务器上的真实物理路径；
- 不同类型图片都可以通过统一出口访问。

#### 3.2 路径解析策略

核心读取逻辑封装在 `readImage` 方法中。

默认情况下，方法会先拼接图片目录路径：

- `/file/images/{imageFolder}/{imageName}`

但如果 `imageFolder` 是以下特殊目录，则走单独分支：

- `temp`：读取 `/file/temp/{imageName}`
- `avatar`：读取 `/file/avatar/{imageName}`

这样处理的原因是：

- 普通业务图片存储在 `images/月份目录/文件名`
- `temp` 和 `avatar` 并不位于 `images` 目录下
- 因此不能使用同一条路径模板强行拼接

这种路径分流设计虽然写法简单，但逻辑上非常关键。它把“图片访问路径规则”统一收拢到了一个方法里，避免前端或其他 Controller
重复关心目录差异。

#### 3.3 响应输出与缓存策略

读取到文件后，接口会：

- 从文件后缀中解析图片类型；
- 设置 `Content-Type` 为 `image/xxx`；
- 通过 `FileInputStream + ServletOutputStream` 将字节流写回响应。

在缓存策略上做了一个细节区分：

- **头像目录不设置缓存**
- **其他图片设置 1 天缓存**：`Cache-Control: max-age=86400`

这个策略很合理：

- 普通图片通常内容稳定，可以走缓存降低重复请求压力；
- 头像更新频率相对更高，如果缓存过久，前端可能长时间看到旧头像；
- 因此头像目录更适合走实时读取。

#### 3.4 边界处理

`readImage` 中还做了一些轻量兜底：

- `imageFolder` 或 `imageName` 为空时直接返回；
- 文件不存在时直接返回，不抛异常；
- 流关闭放在 `finally` 中，避免资源泄漏；
- 异常被记录到日志中，便于后续排查。

这种处理比较符合静态资源读取接口的特点：

- 它不属于强业务事务接口；
- 读取失败时更重要的是不影响服务稳定性；
- 同时需要把问题信息保留在日志中，而不是把底层异常直接暴露给前端。

## 四、发表评论接口开发：`/comment/postComment`

### 1. 接口作用

`/comment/postComment` 用于完成文章评论的发布，支持两种典型场景：

- 发表评论主楼（一级评论）
- 回复已有评论（二级评论）

同时，它也支持以下内容形式：

- 纯文本评论
- 带图片评论
- 文本 + 图片组合评论

这意味着评论发布接口不仅是“插入一条评论数据”，而是要处理：

- 评论开关校验
- 内容合法性校验
- 文章与父评论存在性校验
- 评论图片上传
- 审核状态设置
- 积分、计数、消息等联动逻辑

### 2. 实现位置

- Controller：`horizonhub-web/.../ForumCommentController#postComment`
- Service：`horizonhub-common/.../ForumCommentServiceImpl#postComment`
- 后续联动：`ForumCommentServiceImpl#updateCommentInfo`

### 3. Controller 层的设计思路

#### 3.1 登录与参数校验前置

接口使用：

- `@GlobalInterceptor(checkLogin = true, checkParams = true)`

这表示：

- 未登录用户不能发表评论；
- 基础参数合法性会在进入方法前先经过统一拦截处理。

接口入参中：

- `articleId` 必填
- `pCommentId` 必填
- `content` 配置了长度限制：最少 `5`，最多 `800`
- `replyUserId` 可选
- `image` 可选

这里的 `pCommentId` 是评论层级判断的关键：

- `0` 表示一级评论；
- 非 `0` 表示回复某条父评论。

#### 3.2 评论开关校验

接口开始后，首先读取系统配置：

- `SysCacheUtils.getSysSetting().getCommentSetting().getCommentOpen()`

如果评论功能关闭，则直接抛出异常：

- `当前系统已关闭评论功能`

这一步和评论加载接口保持了一致的设计原则：**功能开关尽量在入口处前置处理**。

#### 3.3 内容与图片不能同时为空

为了支持“图片评论”，本接口允许 `content` 为空；

但为了防止出现真正的空评论，又增加了一条约束：

- `image == null && StringUtils.isBlank(content)` 时直接拒绝。

这条规则比较重要，它保证了评论至少要有一种有效内容。

#### 3.4 对评论内容做 HTML 转义

在 Controller 层中，评论内容会先经过：

- `StringTools.escapeHtml(content)`

处理之后再写入评论对象。

这一步是非常必要的安全措施，目的是防止用户提交带有恶意脚本的内容，降低 XSS
风险。也就是说，本次实现并不是单纯地做“字符串保存”，而是把输入安全控制纳入了评论入口的一部分。

#### 3.5 组装评论对象

Controller 层会从 Session 中取出当前登录用户信息，并组装 `ForumComment`：

- `userId`
- `nickName`
- `userIpAddress`（当前代码中记录的是省份信息）
- `pCommentId`
- `articleId`
- `content`
- `replyUserId`
- `topType = NO_TOP`

然后将评论对象和可选图片一起交给 Service 层处理。

这样的职责划分比较合理：

- Controller 负责组织请求数据；
- Service 负责决定这条评论能不能发、如何发、发出去后要联动哪些业务。

### 4. Service 层完整业务链路

#### 4.1 校验文章是否存在且已审核

评论不是独立业务，它依附于文章存在。因此在 Service 中第一步就会查询文章：

- 如果文章不存在；
- 或文章状态不是 `AUDIT`

则直接拒绝评论。

这样可以避免用户评论未发布、未审核或无效的文章内容。

#### 4.2 校验父评论是否存在

如果 `pCommentId != 0`，说明当前提交的是二级评论，此时必须验证父评论是否存在。

- 父评论不存在，则抛出：`回复的评论不存在`

这一步保证了评论树结构的正确性，避免出现挂在不存在节点下的脏数据。

#### 4.3 校验被回复用户是否存在

如果本次提交传入了 `replyUserId`，则进一步查询用户信息：

- 用户不存在，则拒绝发布；
- 用户存在，则将其昵称写入 `replyNickName`。

这一点对前端展示很重要，因为回复评论通常需要展示“回复某某”的信息。提前把被回复人的昵称落库，可以减少后续查询时的额外关联成本。

#### 4.4 评论图片上传

如果本次评论附带图片，则在 Service 中调用：

- `fileUtils.uploadFile2Local(image, FileUploadTypeEnum.COMMENT_IMAGE, Constants.FILE_FOLDER_IMAGE)`

上传成功后，将返回的相对路径写入：

- `comment.setImgPath(fileUploadDto.getLocalPath())`

这说明评论图片并不是由 Controller 直接落盘，而是交给通用上传工具统一处理。好处是：

- 后缀校验规则一致；
- 路径组织方式一致；
- 缩略图处理逻辑一致；
- 后续如果评论图片目录策略调整，业务层几乎无需改动。

#### 4.5 根据系统配置决定审核状态

评论发布后，并不一定立即对外可见。

当前实现会读取系统设置中的评论审核开关：

- `SysCacheUtils.getSysSetting().getAuditSetting().getCommentAudit()`

然后决定评论初始状态：

- 开启审核：`NO_AUDIT`
- 不开启审核：`AUDIT`

这一步非常关键，它把“评论是否立即生效”的控制权交给了系统配置，而不是写死在业务代码里。

#### 4.6 插入评论并处理后续联动

评论插入数据库之后，如果当前开启了评论审核，则方法直接返回，不再执行后续联动。

原因是：

- 未审核评论不应该立即计入文章评论数；
- 也不应该立刻触发积分奖励和消息通知；
- 这些动作应该等评论真正审核通过后再发生。

如果当前不需要审核，则继续执行 `updateCommentInfo(...)`，完成评论发布后的联动操作。

### 5. 评论发布后的联动处理

`updateCommentInfo(...)` 方法并不是简单的“补一点附加逻辑”，而是本次评论发布闭环里很重要的一层业务编排。

#### 5.1 用户积分奖励

系统会读取评论配置中的奖励积分：

- `commentIntegral`

如果积分值大于 `0`，则调用用户积分服务，为当前评论用户增加积分。

这体现了评论模块和用户成长体系之间的联动关系：评论不仅是互动行为，也会反向激励用户参与社区内容建设。

#### 5.2 一级评论增加文章评论数

只有当 `pCommentId == 0` 时，才会增加文章的评论总数。

这样设计非常合理，因为通常文章评论数统计的是主评论数量，而不是把所有楼中楼都算进去。这样页面上的评论数与用户直观认知会更一致。

#### 5.3 生成站内消息

评论发布后，系统会构造一条 `UserMessage`，消息类型为评论消息。

消息中会保存：

- 文章 ID
- 评论 ID
- 发送人 ID 与昵称
- 评论内容
- 文章标题
- 消息状态（未读）

真正重要的是接收人的判定逻辑。

#### 5.4 不同评论场景下的消息接收人

当前实现按评论层级和回复对象做了分支：

1. **一级评论**
    - 接收人：文章作者

2. **二级评论，但未指定 `replyUserId`**
    - 接收人：父评论作者

3. **二级评论，且指定了 `replyUserId`**
    - 接收人：被回复用户

这套规则保证了消息通知能够尽可能准确地送达“最应该被提醒的人”。

#### 5.5 自己评论自己时不发消息

最后还有一个细节保护：

- 如果发送人和接收人是同一个用户，则不发送站内消息。

这避免了用户给自己评论或回复自己时收到无意义通知，减少消息系统噪音。

### 6. 一级评论与二级评论的返回差异

本次接口在返回结果上还做了一个比较实用的区分。

#### 6.1 一级评论

如果 `pCommentId == 0`，接口直接返回当前新建的评论对象。

这种返回方式适合前端把新评论直接插入一级评论列表。

#### 6.2 二级评论

如果 `pCommentId != 0`，接口不会只返回当前这一条子评论，而是：

- 重新按父评论 ID 查询该父评论下的子评论列表；
- 按二级评论排序规则返回完整 children 列表。

这么做的价值在于：

- 前端无需自己拼装楼中楼结构；
- 回复成功后可以直接刷新当前父评论下的回复区；
- 同时，如果存在“当前用户自己发表但未审核的评论也要看到”的场景，查询时通过 `currentUserId` 也为这种需求预留了支持。

## 五、与通用能力的协同点

本次开发虽然集中在 `FileUtils`、`FileController` 和 `postComment`，但它们能够保持结构清晰，离不开项目里已有通用能力的协同。

### 1. 拦截器统一负责登录与参数校验

通过 `@GlobalInterceptor` 和 `@VerifyParam`：

- 是否登录
- 参数是否缺失
- 字段长度是否合法

这些校验可以在接口入口统一完成，避免 Controller 中堆积大量重复的 if 判断。

### 2. 常量统一目录和后缀规则

`Constants` 中统一定义了：

- `/file`
- `temp`
- `avatar`
- `attachment`
- `images`
- 图片后缀白名单
- 附件后缀白名单

这样可以保证上传、保存、读取三端使用的是同一套目录规则，减少硬编码带来的路径不一致问题。

### 3. 枚举统一业务状态

本次功能中大量使用了枚举来统一表达业务状态，例如：

- `FileUploadTypeEnum`
- `CommentStatusEnum`
- `CommentTopTypeEnum`
- `ArticleStatusEnum`
- `MessageTypeEnum`

这种做法可以明显提升代码可读性，也让文档描述和实际实现更加一致。

### 4. 系统设置缓存统一承接功能开关

评论是否开启、评论是否需要审核、评论奖励积分等系统级配置，都是通过 `SysCacheUtils` 在内存中统一读取。

这意味着：

- 配置逻辑和业务逻辑是解耦的；
- 不需要在每次请求时都重复查数据库；
- 功能是否开放、评论是否立即可见，都可以通过系统设置动态控制。

## 六、设计总结

回顾本次完成的工作，可以把核心设计思路概括为以下 3 点。

### 1. 文件能力要统一入口、统一规则、按业务分流

`FileUtils` 负责把上传能力沉到通用层，用上传类型枚举来区分文章封面、附件、评论图片、头像等不同业务场景。这样既减少了重复代码，也为后续扩展更多文件类型留出了空间。

### 2. Controller 轻量化，Service 承担核心业务规则

在评论发布场景中，Controller 主要负责：

- 接收参数
- 基础校验
- 安全转义
- 组织评论对象

真正和业务强相关的逻辑，例如：

- 文章是否存在
- 父评论是否合法
- 被回复用户是否存在
- 是否需要审核
- 是否发积分
- 是否发消息

都放到了 Service 层完成。这种分层方式后续更容易维护，也更适合继续扩展评论相关能力。

### 3. 评论发布不是单点功能，而是业务闭环的一部分

本次实现的 `postComment` 并不是简单插入一条评论记录，而是把评论发布纳入了完整业务链路：

- 内容安全控制
- 图片上传
- 审核状态流转
- 文章评论数更新
- 用户积分奖励
- 站内消息通知

从这个角度看，本次工作实际上补齐了评论模块从“能看、能点赞、能置顶”到“真正能发布”的关键一步。

---

## 七、小结

本次工作完成后，系统在“文件服务”和“评论发布”两个方向上都向前推进了一大步：

- `FileUtils` 为后续各类上传场景提供了统一的基础能力；
- `FileController` 打通了图片上传、头像读取、通用图片访问的接口链路；
- `postComment` 则补齐了评论模块最核心的发布能力，并与审核、积分、消息等业务完成了联动。

如果说前面的工作更多是在补评论的“展示与互动能力”，那么本次内容则进一步补齐了评论的“输入能力”和文件系统的“存取能力”。这为后续继续完善文章封面上传、附件管理、头像更新、评论审核流转等功能打下了比较扎实的基础。
