# 02 开发环境自动登录后门隔离

> 涉及提交：`ca2a47a` fix: 用 @Profile 物理隔离开发环境自动登录后门

## 原来的实现

为方便本地开发免登录，两端拦截器里都有一段「开发模式自动登录」逻辑。

### web 端 `LoginInterceptor.preHandle`

```java
HttpSession session = request.getSession();
SessionWebUserDto sessionUser = (SessionWebUserDto) session.getAttribute(SESSION_KEY);
if (sessionUser != null) return true;
// 如果配置文件写明是开发环境，则所有接口不校验是否已登录
if (webConfig.getIsDev()) {
    // ...自动创建测试账号...
    sessionUser.setAdmin(true);          // 直接授予管理员
    session.setAttribute(Constants.SESSION_KEY, sessionUser);
    return true;
}
throw new BusinessException(ResponseCodeEnum.CODE_901);
```

### admin 端 `AppInterceptor.checkLogin`

```java
SessionAdminUserDto sessionUser = (SessionAdminUserDto) session.getAttribute(SESSION_KEY);
if (sessionUser == null && appConfig.getIsDev()) {
    sessionUser = new SessionAdminUserDto();
    sessionUser.setAccount("管理员");      // 直接签发管理员会话
    session.setAttribute(Constants.SESSION_KEY, sessionUser);
}
```

开关仅靠 yml 里一个布尔值 `isDev.open` 控制（`AppConfig` 的 `@Value("${isDev.open:false}")`）。

## 存在的问题

**这是全站最危险的隐患**：只要 `isDev.open=true`，**任何未登录请求**都会被自动签发**管理员会话**——web 端 `setAdmin(true)`，admin 端直接构造管理员 DTO。

- 默认虽为 `false`，但**没有任何编译期 / 加载期保护**。
- 一旦生产环境配置误写 `isDev.open=true`，等于无密码管理员后门：任意人可发帖、删帖、改积分、调后台写接口。
- 引入 AI 后更致命：AI 代理若接入写操作接口，叠加此后门 = 任意人可让 AI 以管理员身份操作。

## 改进后的实现

核心思路：把「自动登录」从「运行期布尔开关」改为「Bean 级别的 profile 隔离」，让生产构建**在类加载期就剔除该分支**。

### 1. 把自动登录逻辑抽成独立 Bean，并用 `@Profile("dev")` 标注

web 端 `DevWebAutoLoginHandler`：

```java
@Component
@Profile("dev")
public class DevWebAutoLoginHandler {
    public boolean createDevSession(HttpSession session) {
        // 原来的「创建测试账号 + 授予管理员 + 写 session」逻辑搬到这里
        ...
    }
}
```

admin 端 `DevAdminAutoLoginHandler` 同理。

### 2. 拦截器用 `@Autowired(required = false)` 可选注入

```java
@Autowired(required = false)
private DevWebAutoLoginHandler devWebAutoLoginHandler;
...
// 仅 dev profile 下 Bean 存在；生产环境 devWebAutoLoginHandler == null，此分支不可达
if (devWebAutoLoginHandler != null) {
    return devWebAutoLoginHandler.createDevSession(session);
}
throw new BusinessException(ResponseCodeEnum.CODE_901);
```

### 3.（附带修复）admin 白名单由子串匹配改为精确匹配

原 `AppInterceptor` 用 `request.getRequestURI().contains("login")` / `contains("checkCode")` 做免登录白名单（子串匹配，存在绕过面）。改为：

```java
private static final Set<String> WHITELIST = Set.of("/checkCode", "/login");
...
if (WHITELIST.contains(request.getServletPath())) {   // 用 servletPath 排除 context-path，精确匹配
    return true;
}
```

## 如何工作（改造后）

- **生产环境（未激活 `dev` profile）**：`@Profile("dev")` 的两个 Handler Bean 不会被创建 → 拦截器注入得到 `null` → `if (handler != null)` 分支不可达 → 任何未登录请求都抛 `CODE_901`。
- **开发环境**：以 `--spring.profiles.active=dev` 启动时，两个 Bean 才存在，自动登录生效。
- 关键区别：以前是「prod 也加载了这段代码，只是靠布尔值关掉」；现在是「prod 根本不加载这段代码」。误配 `isDev.open=true` 不再能触发后门。
- `getServletPath()` 返回不含 context-path 的路径（如 `/login`），不受 `/api` 前缀影响，白名单更稳。

## 验证 / 注意事项

- 启用免登录开发模式的正确方式是 `--spring.profiles.active=dev`（而非设 `isDev.open`）。
- `application.yml` 默认 `spring.profiles.active=${SPRING_PROFILES_ACTIVE:dev}`，即本地默认就是 dev，开箱即用；生产必须显式 `prod`（见 [03-凭据与profile.md](03-凭据与profile.md)）。
